**Дата:** 2026-08-17 · **Статус:** рабочий документ, обновляется · **Автор контекста:** Arena-агент

---

## 1. Короткий ответ на поставленный вопрос

> Стоит ли формировать полную базу (граф, онтологии) для агента типа Antigravity, или только настроить MCP, чтобы он сам всё искал? Или готовый датасет, нативно переведённый в базу? Или другой вариант?

**Ни один из трёх вариантов в чистом виде. Правильный ответ — гибрид из трёх ярусов памяти + MCP как «живой» слой-источник, и всё это подчинено главному контуру: локальный симулятор → оптимизация → сабмиты → анализ реплеев → обратно в память.**

| Вариант | Вердикт | Почему |
|---|---|---|
| Полный граф/онтология сразу | ❌ Не делать в первую неделю | Домен игры мал и уже структурирован (открытый движок + README). Онтология дорога в обслуживании, а мульти-хоп запросов, ради которых нужен граф, на старте почти нет. Граф — это инструмент, который докупается по мере появления реальных relational-запросов. |
| Только MCP («пусть сам ищет») | ⚠️ Недостаточно | MCP даёт **доступ** (метаданные: треды, лидерборд, эпизоды, датасеты), но не **память**. Каждая сессия агента будет начинать с нуля, без дистилляции и накопления опыта. К тому же MCP-поиск по Kaggle — это поиск по метаданным, а не «понимание, за счёт чего строилась победа». |
| Готовый датасет → база | ✅ Да, но только как один из слоёв, и не тот датасет | Meta Kaggle / сборники решений табларных соревнований переносятся в эту задачу слабо: Kaggriculture — **симуляционное** соревнование (игра), а не табличный ML. Ценный «датасет» здесь — **реплеи топ-агентов, которые организаторы публикуют ежедневно (до 20 ГБ)**, плюс открытый исходник движка. |
| Другой вариант | ✅ **Гибрид (рекомендуется)** | Три яруса памяти по образцу Antigravity (KI/Skills/Artifacts) и Letta (core/recall/archival) + MCP как конвейер пополнения + дисциплина «маленького мозга» (brain.md со строгим лимитом). |

## 2. Факты о соревновании, которые определяют архитектуру

Собрано из страницы соревнования, правил и открытого исходника движка.

### 2.1 Формат
- **1v1, пошаговая ферма.** 720 ходов = 30 дней × 24 хода. Побеждает больше денег в банке на конец сезона.
- **Рейтинговая система** (аналог Elo/Trueskill): только победа/поражение/ничья, амплитуда зависит от разницы рейтингов. **Финал — турнир Брэдли-Терри** на накопленных эпизодах.
- **5 сабмитов в день, активны только 2 последних.** Это ключевое: соревнование — это **мартингейл коротких итераций**, а не одна большая модель.
- Призовой фонд $50k (10 мест по $5k). Победители обязаны открыть код (CC-BY 4.0) и описать метод.

### 2.2 Технические ограничения сабмишена (критично для гипотезы «LLM играет сам»)
- Размер: **100 МБ**, ресурсы: **1.6 vCPU, 6.5 ГБ RAM, 8 ГБ диск**.
- **`actTimeout: 1`** — 1 секунда на ход (из `kaggriculture.json` движка).
- **Правило 12: NO INGRESS OR EGRESS** — во время эпизода нельзя обращаться к внешним API и отправлять данные наружу.

→ **Вывод: LLM физически и юридически не может играть внутри эпизода.** Его роль — **внешний контур**: анализ, генерация кода политики, дизайн экспериментов, дистилляция знаний. В сабмит уходит скомпилированный детерминированный/обученный агент. Это ровно паттерн «LLM-ассистент гроссмейстера», а не «LLM за игровым столом».

### 2.3 Открытые активы (готовые источники для базы)
1. **Открытый движок:** `Kaggle/kaggle-environments/kaggle_environments/envs/kaggriculture/` — `kaggriculture.py` (40 КБ, полная механика), `README.md` (таблицы урожайности, ценовые функции), `AGENTS.md` (инструкция для агентов-разработчиков). Есть и упрощённый `kaggriculture_beginner`.
2. **Ежедневный датасет реплеев топ-агентов** — `kaggle/kaggriculture-episodes-index` (до 20 ГБ/день), публикуется организаторами **специально для imitation learning / behavior cloning / bootstrapping RL**. Это самый ценный «готовый датасет» в этом соревновании.
3. **Публичные реплеи каждого эпизода** (через CLI: `kaggle competitions replay <id>`).
4. **Форум** — очень активный: баланс-патчи, треды «Is Pure Self-Play PPO viable?», «Documentation vs. Engine Discrepancies» (участники уже нашли расхождения доков и движка!), «How I Keep Iterating», официальный Discord.
5. **Питон-пакет `kaggle-environments`** — движок ставится локально, партии гоняются тысячами без сабмитов.

### 2.4 Важные нюансы, влияющие на стратегию
- Организаторы уже вносили **баланс-изменения** (2 пина на форуме) → база должна вести **changelog механик**; источник истины — исходник движка, а не доки (доки и движок расходятся, это подтверждено на форуме).
- Рынок детерминированно моделируется: ценовые функции (linear/sq/sqrt/log/hinge) заданы таблицей с `T`, `I0`, `base`, `target` → **оптимальную политику продаж/закупок можно считать оптимизатором, а не только учить**.
- Агент видит публичное состояние фермы оппонента (но не его сарай) → возможна **адаптация к поведению оппонента в ранней фазе игры** (стандартный приём в симуляционных соревнованиях).

## 3. Что показало исследование источников

### 3.1 Как выигрывались похожие соревнования (Lux AI S1–S3, Halite, Kore, Hungry Geese, BattleSnake)
- Общий паттерн побед в симуляционных 1v1/multi соревнованиях: **(а) быстрый локальный симулятор**, (б) скелет стратегии правилами + (в) оптимизация параметров/обучение поверх, (г) гибриды «правила + RL», (д) ежедневный цикл сабмит-анализ-итерация.
- В Lux AI S3 (NeurIPS 2024, тот же хостинг-формат: JAX-окружение, Trueskill-рейтинг, обязательный open source победителей) призёры использовали PPO self-play с тщательным reward shaping, а часть топов — быстрые rule-based с оптимизацией; организаторы отдельно отмечали ценность «датасета реплеев сильных агентов».
- Ссылки: [Lux AI S3 overview](https://openreview.net/pdf?id=7t8kWYbOcj), [сборники решений Kaggle Simulations](https://farid.one/kaggle-solutions/).

### 3.2 Агенты, решающие Kaggle-задачи (релевантная академическая база)
- **MLE-bench** (OpenAI, ICLR 2025, [arXiv:2410.07095](https://arxiv.org/abs/2410.07095)): лучшие агенты получают медаль лишь в ~17% соревнований; **скаффолдинг важен, но узкое место — базовая модель**; «знакомство» модели с соревнованием (contamination) коррелирует с результатом слабо. → Знание «как побеждали» полезно, но не заменит итерационного цикла.
- **Agent K** ([arXiv:2411.03562](https://arxiv.org/abs/2411.03562)): цикл обучения по Колбу, **репозиторий опыта из решённых задач + case-based retrieval**; Elo-MMR 1694 — выше медианы Kaggle Masters; 9 gold/8 silver/12 bronze. → **Самое прямое доказательство: структурированная, дистиллированная память опыта даёт измеримый прирост.** Но форма памяти там — не граф, а **библиотека структурированных кейсов (задача→решение→урок)**.
- **Konwinski Prize** / REPO-BENCH: та же картина — агентам нужен curated workspace, а не гигантская онтология.

### 3.3 Архитектуры памяти агентов (что говорит литература)
- Сводный вывод ([zylos.ai](https://zylos.ai/research/2026-04-05-ai-agent-memory-architectures-persistent-knowledge/), [FalkorDB](https://www.falkordb.com/blog/ai-agent-memory-retrieval-architecture/), обзоры по agentic memory): **векторный поиск хорош для одношаговых фактов; граф — для мульти-хоп реляционных запросов; продакшн-стандарт — гибрид**. Практическая эвристика: **начинай с простого (markdown + SQLite FTS / вектор), граф докупай, когда реально появятся реляционные запросы** («что связано с X, что изменилось после Y»).
- **Letta/MemGPT**: иерархия core memory (всегда в контексте, ~2–4 КБ) / recall (журнал) / archival (внешнее хранилище) — идеальный шаблон для нашего случая.
- **Antigravity** (Google DeepMind, agent-first IDE): KI (Knowledge Items — дистиллированные факты с метаданными), Skills (процедурное знание «как делать X»), Artifacts (прозрачная документация работы). Пользовательская практика ([Reddit](https://www.reddit.com/r/google_antigravity/comments/1tbvmnb/how_i_gave_google_antigravity_a_real_longterm/)): **`brain_context.md` со строгим лимитом строк (перезапись/конденсация вместо аппенда) + `todo.md` + журнал ошибок** — работает лучше, чем большие автономные базы. → Механизм, который стоит скопировать у Antigravity, — это **дисциплина дистилляции (KI)**, а не знаниевый граф.

### 3.4 MCP-серверы Kaggle (что реально дают)
- Обёртки над Kaggle API: [54yyyu/kaggle-mcp](https://github.com/54yyyu/kaggle-mcp) (competitions, datasets, kernels, models, discussions), Galaxy-Dawn Kaggle-MCP (21 инструмент, включая search/list/detail discussions + загрузка датасетов), официальный Kaggle API (CLI: `competitions`, `episodes`, `replay`, `logs`, `leaderboard`).
- **Что MCP даёт здесь:** лидерборд, новые треды форума, статусы сабмитов, список эпизодов, скачивание реплеев, ежедневный индекс топ-эпизодов. Это **конвейер живого интела**, а не знаниевая база.
- **Ограничение:** выдаёт метаданные; «понимание побед» всё равно должен дистиллировать агент.

### 3.5 Готовые датасеты (HG и прочие)
- Meta Kaggle (соревнования+сабмиты+форумы за годы) — полезен для общего «как устроен Kaggle», но для симуляционного соревнования ценности мало: **знания из табларных/vision-решений не переносятся на игру**.
- Сборники writeup'ов победителей ([farid.one/kaggle-solutions](https://farid.one/kaggle-solutions/), GitHub-коллекции) — полезны **выборочно**: симуляционные соревнования (Lux, Halite, Kore, Hungry Geese, BattleSnake) и агентные (ARC, LLM Science).
- HF: зеркала конкретных соревнований (Kaggle-LLM-Science-Exam и т.п.), цельного «датасета знаний о победах» нет — и не предвидится, потому что ценность создаёт дистилляция, а не сырьё.

## 4. Рекомендуемая архитектура (решение)

### 4.1 Три яруса памяти (в духе Antigravity/Letta, подтверждено Agent K)

**Ярус 1 — «Мозг» (core memory, всегда в контексте, ~150 строк):**
- `docs/brain.md` — состояние проекта: что известно, текущая гипотеза, что тестируем, что сломалось, приоритеты. **Жёсткий лимит, конденсация вместо аппенда** (приём из практики Antigravity).
- `docs/todo.md` — ближайшие шаги, выполненные удаляются.
- `docs/lessons.md` — журнал ошибок и уроков (чтобы не наступать дважды).

**Ярус 2 — Курируемая структурированная база (semantic memory, в git):**
- `docs/engine-spec.md` — дистилляция механик из исходника движка (истина — `kaggriculture.py`, не доки) + changelog баланс-патчей.
- `docs/strategy/` — карточки стратегий: «wheat-loop», «egg-empire», «melon timing»… по шаблону **задача → решение → урок** (шаблон Agent K).
- `docs/opponents.md` — профили мета-стратегий, встречающихся на лестнице (из реплеев).
- `db/experiments.sqlite` (+FTS5) — **реестр экспериментов**: версия агента, параметры, ELO-оценка в self-play, против кого тестировалась, вывод. Это и есть «база, на которой строится победа»: отслеживаемость даёт compounding.
- Граф/онтология — **отложить**: домен покрывается 2–3 десятками понятий (культура, животное, рынок, заказ); онтологию нарисуем в одном markdown. Переход на графовую БД (гибрид типа Graphiti/Mem0) — **триггер-условие**: когда появятся реальные мульти-хоп запросы к реплеям («какие цепочки закупок предшествовали покупке NE-квадранта у победителей»). До этого SQLite + файлы быстрее и надёжнее.

**Ярус 3 — Сырой архив (archival memory, НЕ в git):**
- `data/replays/` — скачанные реплеи (свои и из daily top-episodes index).
- `data/episodes-index/` — ежедневный CSV-индекс топ-эпизодов.
- логи сабмитов, веса моделей. В git — только манифесты/скрипты загрузки.

### 4.2 MCP — как слой-источник, а не как память
Настроить один раз (Kaggle API + MCP-обёртка, у нас уже есть CLI-доступ), и использовать как **конвейер пополнения** ярусов 2–3:
- ежедневно: новый индекс топ-эпизодов → скачать → прогнать статистику → апдейт `opponents.md` и `brain.md`;
- новые треды форума → выжимка в `lessons.md`;
- статусы своих сабмитов и рейтинг → в реестр экспериментов.
Живые разовые запросы (лидерборд, чужой реплей) MCP закрывает отлично.

### 4.3 Главный контур, ради которого всё это заводится (то, что реально выигрывает)
```
1. Локальный симулятор (движок открыт!) → тысячи партий/час, без лимитов сабмитов
2. Скелет политики (rule-based) + оптимизатор параметров (рынок детерминирован — многое считается)
3. Сабмит ≤2 активных версий → рейтинг на живой лестнице
4. Анализ реплеев (своих и топ-агентов из ежедневного датасета)
5. Дистилляция выводов в ярусы 1–2 → новая гипотеза → цикл
Опционально (неделя 3+): self-play RL поверх скелета (PPO/эволюция), если
rule-based упрётся в потолок — тред «Is Pure Self-Play PPO viable?» говорит,
что сообщество это уже проверяет.
```
Роль LLM-агента: аналитик, генератор кода политики, дизайнер экспериментов, дистиллятор. Роль базы знаний: **сделать каждую итерацию умнее предыдущей** (это и есть «понимание, за счёт чего строилась победа» — накопленное и структурированное).

## 6. Риски и открытые вопросы

1. **Баланс-патчи** — самый большой риск для заученных стратегий; митигация: база ведёт changelog, агент параметризуется, а не хардкодится.
2. **Гонка в RL** — если мета уйдёт в self-play PPO, rule-based может не догнать; митигация: фаза 2 закладывает RL-опцию заранее (каркас окружения готов с фазы 0).
3. **Рейтинговая дисперсия** — на лестнице шум (мало эпизодов на версию); митигация: локальный ELO-замер в self-play + против фиксированных reference-агентов (`starter`, скачанные политики), решения принимать по агрегату, а не по одному матчу.
4. **Масштаб базы** — 20 ГБ/день реплеев нельзя «загрузить в контекст»; митигация: база хранит не реплеи, а **статистики и карточки-выводы**; сырьё живёт в ярусе 3.
5. Открытый вопрос для обсуждения: **нужен ли нам граф сейчас** (мой ответ — нет, триггеры см. §4.1) и **какую модель LLM держать во внешнем контуре** (Gemini/Claude/GPT — по критерию качество/стоимость для дистилляции и генерации кода).
